BotState Model

This document defines the working behavior model for playerbot planning.
It is intentionally architecture-first rather than file-first.

Runtime Source

BotState.h defines the runtime states as:

- BOT_STATE_COMBAT
- BOT_STATE_NON_COMBAT
- BOT_STATE_DEAD
- BOT_STATE_REACTION
- BOT_STATE_ALL

For this model:

- COMBAT maps to CO
- NON_COMBAT maps to NC
- DEAD maps to DEAD
- REACTION maps to REACT
- ALL is not a runtime state tree; it is meta/cross-state only

Core Planning Rule

Behavior should be modeled as:

- choose intent first
- then choose target and method
- then validate whether the action is currently possible
- then move if needed
- then execute

This keeps travel as movement support instead of letting it become the top-level planner.

Canonical Planning Key

The planning identity for a bot action can be written as:

state / coordination / task / stage / focus

Examples:

- NC / solo / quest / accept / Marshal Dughan
- NC / group / quest / progress / Hogger
- NC / solo / maintenance / repair / Smith Argus
- CO / group / quest / progress / Hogger
- DEAD / group / quest / progress / Hogger

Interpretation:

- state
  - NC, CO, DEAD, REACT
- coordination
  - solo, group
- task
  - quest, maintenance, skills, social, economy, gather, idle
- stage
  - task-specific phase such as accept, progress, turn in, repair, mail, herb
- focus
  - the concrete target, area, object, npc, mob, or leader-directed objective

Group Context Slice

Group is selected as an NC task family, but it also exports shared context to the other states.

NC.group produces:

- who is leader?
- who do I follow?
- where is the rally point?
- what is the party objective?
- what is my role?

That context is then consumed by:

- CO
  - assist leader target
  - defend group member
  - clear blocker on party path
  - hold formation instead of solo chasing
- DEAD
  - recover toward party location
  - rejoin party after revive
- REACT
  - retreat with group
  - help threatened ally
  - respond to party emergency context

Design Notes

- travel is not a top-level planner
  - it belongs under Reposition / Travel
- group is an NC task family and a cross-state context producer
- dungeon is not an NC task family
  - it is a mode overlay that changes behavior across NC, CO, DEAD, and REACT
- combat-support belongs in CO, not NC
- recovery belongs in DEAD, not NC
- food and buff upkeep belong under maintenance
- loot is usually a target/method or follow-up action, not a top-level task family

Usage Rule

When diagnosing behavior or deciding where logic should live:

- first identify the state
- then identify coordination
- then identify the selected task
- then identify the task stage
- then identify the concrete focus

After that, classify the logic by step:

- Select Task
- Select Target / Method
- Validate Actionability
- Reposition / Travel
- Execute Action
